## Correct heartbeat deadline accounting

A serious remaining bug affects the execution budget.

`macos_runner.py` captures `process_started_at` before SQL preflight, schema validation, target loading, and quota recovery.

It later passes that earlier timestamp into `Collector.run_once()`.

`HeartbeatBudget` then creates a new monotonic deadline using the old process-start timestamp, without correctly deducting the time already spent during preparation.

A controlled scenario demonstrates:

- Process started at 12:00 UTC.
- SQL initialization completed at 12:02 UTC.
- Logical bucket ends at 12:05 UTC.
- Actual remaining time is 180 seconds.
- Existing calculated budget can still report 295 seconds.

Fix this at the execution-contract level.

Requirements:

- Preserve the original UTC logical bucket identity.
- Use the actual current execution time and the absolute bucket deadline when establishing the remaining budget.
- Include process startup, SQL preparation, credential resolution, schema validation, and quota recovery in the elapsed time.
- Do not reset the heartbeat budget after initialization.
- Maintain a monotonic clock for elapsed duration measurements.
- Use reliable UTC wall-clock/deadline checks for real bucket boundaries.
- Recheck remaining time before starting each target, SQL authorization, and network transmission.
- Reject network work when insufficient real time remains.
- Preserve the approved safety margin.
- Distinguish startup delay, late dispatch, insufficient budget, and in-flight overrun.
- Never transmit catch-up requests for historical buckets.

Add regression coverage for slow startup and SQL initialization, including a two-minute preflight inside a five-minute bucket.

Verify that no code path can extend an expired bucket merely by creating a new budget object.
