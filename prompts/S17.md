Include the following requirements.

--------------------------------------------------
1. PROSPECTIVE COLLECTION IS REQUIRED
--------------------------------------------------

Stage 02 historical tests established:

1D:
HISTORICAL_TIMETABLE_ONLY

7D:
HISTORICAL_TIMETABLE_ONLY

30D:
HISTORICAL_TIMETABLE_ONLY

90D:
HISTORY_NO_EVENT for the specific tested request

180D:
HISTORY_NO_EVENT for the specific tested request

Therefore:

- do not assume MDD can reconstruct past realtime state
- do not rely on later retrospective queries to recover missed estimates
- missed collector observations may represent permanently lost realtime
  evidence
- future collector reliability matters

Do not claim an exact MDD retention cutoff.

--------------------------------------------------
2. PRESERVE SOURCE TIMESTAMPS
--------------------------------------------------

When available, retain independently:

- TimetabledTime
- EstimatedTime
- RecordedAtTime
- EstimatedTimeLow
- EstimatedTimeHigh
- request/observation timestamp
- response timestamp where meaningful
- arrival vs departure timing context
- call scope:
  PreviousCall / ThisCall / OnwardCall

Never persist only a derived delay while discarding the source timestamps.

--------------------------------------------------
3. NEVER PROMOTE ESTIMATE TO ACTUAL
--------------------------------------------------

The collector must never infer:

last EstimatedTime == actual arrival/departure

or:

past EstimatedTime == RecordedAtTime

EstimatedTime remains prediction even after the event has passed.

Actual performance requires a validated actual-time field/source.

--------------------------------------------------
4. PRESERVE ESTIMATE EVOLUTION
--------------------------------------------------

Future design should be capable of preserving multiple observations of the
same service event over time when analytically justified.

This enables future questions such as:

- how predictions changed approaching arrival
- prediction stability
- prediction accuracy if an actual timestamp later becomes available
- how early delays become visible

Do not finalize snapshot retention cadence here.

--------------------------------------------------
5. EVENT CORRELATION
--------------------------------------------------

Future collector design must preserve enough source identity to correlate the
same service/call across observations.

Candidate identity inputs include where available:

- OperatingDayRef
- JourneyRef
- LineRef
- DirectionRef
- OperatorRef
- StopPointRef
- TimetabledTime
- StopSeqNumber
- arrival/departure context

Do NOT prematurely declare one field combination a globally unique production
key before Stage 7 validation.

The design must explicitly validate event identity and deduplication.

--------------------------------------------------
6. OBSERVATION TIME IS FIRST-CLASS DATA
--------------------------------------------------

Every collected realtime observation needs a reliable collection/observation
timestamp.

Without observation time, estimate evolution cannot be reconstructed.

Preserve the distinction between:

- event timetable timestamp
- provider estimated timestamp
- provider recorded timestamp
- collector observation timestamp

--------------------------------------------------
7. OPERATIONAL FLAGS MUST REMAIN INDEPENDENT
--------------------------------------------------

Where available preserve independently:

- Cancelled
- Deviation
- UnplannedStop
- NotServicedStop
- NoBoardingAtStop
- NoAlightingAtStop

Do not collapse them into one generic status.

Do not infer cancellation from missing estimates.

--------------------------------------------------
8. PLATFORM/BAY DATA
--------------------------------------------------

Preserve independently:

- PlannedBay
- EstimatedBay

Do not treat:

missing EstimatedBay = unchanged

Do not call a difference an actual physical platform change without stronger
evidence.

--------------------------------------------------
9. SITUATION DATA
--------------------------------------------------

Preserve:

- situation identity
- SituationFullRef / references
- validity
- summary
- description/detail where approved
- source
- priority
- affected-entity association/scope where available

Do not infer causality between a situation and delay/cancellation merely from
association.

--------------------------------------------------
10. COLLECTION GAPS
--------------------------------------------------

Future collector architecture must make observation gaps explicit.

Collector downtime must not silently appear as:

- no delay
- no realtime
- no cancellation
- no service

Plan for health/audit metadata capable of distinguishing:

source absence
collector failure
transport failure
parsing failure
persistence failure
scheduled non-collection

--------------------------------------------------
11. RETRIES AND QUOTA
--------------------------------------------------

Each retry is another HTTP request.

Future collector design must budget together:

- normal polling
- retries
- all targets
- all collector processes using the same credential where measurable
- overlap/concurrency

The current conservative project ceiling is:

250,000 requests/month

until stronger provider/account evidence supersedes it.

Do not define final production cadence in this document.

--------------------------------------------------
12. IDEMPOTENCY AND DUPLICATES
--------------------------------------------------

The collector must tolerate:

- repeated observations
- retries
- overlapping runs
- the same event appearing in multiple polls

Future persistence must support deterministic deduplication/idempotency while
still preserving analytically meaningful evolution over time.

Do not solve this by discarding every repeated event.

--------------------------------------------------
13. FAILURE CAUSALITY
--------------------------------------------------

Preserve enough audit context to tell apart:

HTTP failure
authorization failure
DNS/network failure
provider application error
parser failure
persistence failure

Do not infer provider outage from a local resolver failure.

--------------------------------------------------
14. RAW RESPONSE POLICY
--------------------------------------------------

Default:

No permanent/automatic full raw-response retention.

For approved diagnostic experiments:

temporary raw evidence outside Git is allowed.

If Stage 7 later requires short-term automated raw capture, it needs explicit
approval for:

purpose
retention
storage
access control
cleanup

15. RecordedAtTime DISCOVERY

Even though RecordedAtTime was not observed in Stage 02:

future collector parsing must NOT discard it if it appears.

It should remain a nullable candidate source field.

Any first observation of RecordedAtTime must trigger semantic/coverage
validation before Actual Delay becomes a production KPI.

Future validation must be capable of observing the SAME event repeatedly
