## Fix automatic rollover with previous-period pending permits

Inspect:

- `MssqlPersistence.recover_stale_quota_permits()`
- `MssqlPersistence.ensure_automatic_quota_rollover()`
- `ctl.uspEnsureMddMacQuotaPeriod`
- Quota authorization and crash-recovery logic.

Current sequencing is unsafe for unattended operation.

`recover_stale_quota_permits()` first invokes automatic rollover.

The SQL rollover procedure rejects prior-period `PENDING_AUTHORIZATION` permits.

As a result, a stale pending permit can block the rollover needed before recovery continues.

Design a safe, bounded and idempotent recovery-before-rollover mechanism.

Requirements:

- Identify prior-period pending permits using verified durable SQL records.
- Use SQL Server authoritative time.
- Respect each permit's genuine expiration and stale-recovery policy.
- Never finalize still-valid in-flight permits prematurely.
- Convert sufficiently stale ambiguous permits to conservative uncertain provider attempts.
- Preserve each permit's original billing-period identity.
- Preserve confirmed provider consumption.
- Never return ambiguous network attempts to available quota.
- Preserve all audit history and original reservation timestamps.
- Avoid moving previous-period attempts into the new month's counter.
- Prevent concurrent recovery and rollover races.
- Preserve SQL transaction atomicity.
- Handle interruption and retry idempotently.
- Block rollover while genuinely unresolved recent permits remain.
- Allow automatic progression after those permits become safely recoverable.
- Avoid requiring a manual SQL intervention merely because a previous worker crashed near month-end.

Validate the full sequence, not only isolated pure functions.

Required scenarios:

- No pending permits.
- One stale previous-period permit.
- Multiple stale permits.
- One recent potentially active permit.
- Mixed confirmed, uncertain, pending and released permits.
- Crash during recovery.
- Crash between recovery and new-period creation.
- Repeated automatic rollover.
- Two concurrent rollover attempts.
- SQL outage followed by recovery.
- End-of-October to November transition.
- Subsequent December and January transitions.

The goal is automatic, conservative self-recovery where evidence supports it, and explicit fail-closed behavior when uncertainty cannot safely be resolved.
