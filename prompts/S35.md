==================================================
DECISION 2 — USE A FIXED DepArrTime ANCHOR
==================================================

The current Stage 7 request contract advances `DepArrTime` using the current
request/reference timestamp.

That is not ideal for the specific goal of observing transient
`RecordedAtTime`.

If the search anchor moves forward after an event occurs, the event may leave
the returned StopEventResult set before a source-provided recorded time can be
observed.

Revise the Stage 8 pilot design to use a FIXED pilot anchor.

At pilot start:

PilotAnchorDepArrTime =
the UTC reference timestamp selected at pilot start.

Use that SAME `DepArrTime` value for every MDD request in the one-hour pilot.

Do NOT advance it with wall clock time during the pilot.

Purpose:

retain a stable cohort of returned arrival events long enough to observe their
lifecycle before and after their scheduled/estimated event time.

This follows the useful fixed-anchor principle already demonstrated by the
bounded near-event lifecycle validation.

The first successful response acts as the initial cohort/baseline observation.

Later responses observe the same fixed search anchor.

Do not require every result position to remain identical.

Result additions/removals/reordering are themselves lifecycle evidence.
