2. PROJECT GEOGRAPHIC SCOPE
==================================================

The authoritative project scope is:

COLOGNE / KÖLN ONLY.

The project is NOT intended to become:

- Germany-wide transport analytics;
- NRW-wide transport analytics;
- complete VRS network analytics;
- complete GTFS.de network analytics.

GTFS.de may provide Germany-wide realtime data, but that does NOT expand the
project scope.

The GTFS-RT feed is a source feed.

It is NOT the analytical scope.

==================================================
3. COLOGNE-INTERNAL ANALYTICAL RULE
==================================================

The core analytical unit is transport activity occurring inside Cologne.

For routes/trips that extend outside Cologne:

- retain/analyze only stop events and service evidence that fall inside the
  approved Cologne scope;
- do NOT use external portions of the trip when calculating Cologne network
  KPIs;
- do NOT report the performance of the entire inter-city / regional route as
  though it were a Cologne-only result.

Example:

A regional train may start outside Köln, pass through several Köln stations,
and continue outside Köln.

The project may analyze:

- its in-scope Köln stop events;
- its in-scope Köln service state;
- its in-scope Köln disruption evidence.

The project must NOT claim:

"the complete route has this performance"

unless the full route is explicitly in a future expanded scope.

==================================================
4. THROUGH-SERVICE RULE
==================================================

Through-services are NOT core route-level KPI subjects.

A through-service may still contribute:

- Cologne stop-event observations;
- Cologne platform evidence;
- Cologne disruption evidence;
- Cologne skipped-stop evidence;
- Cologne estimated-delay observations.

But its outside-Cologne sections must not contribute to Cologne KPI
denominators.

Document this distinction explicitly:

IN-SCOPE STOP EVENT

does NOT automatically mean:

IN-SCOPE FULL TRIP.

10. CANONICAL SERVICE-EVENT MATCHING DIMENSIONS
==================================================

Candidate reconciliation should use multiple independent dimensions.

Potential dimensions include:

- ServiceDate / OperatingDay
- canonical line identity
- canonical stop identity
- direction
- scheduled/timetabled time
- arrival/departure event context
- stop sequence where available
- operator where useful
- adjacent-stop sequence where useful

Do NOT require every source to populate every dimension.

Do NOT use a single weak attribute as proof of identity.

==================================================
11. STOP-EVENT MATCHING BEFORE FULL-TRIP MATCHING
==================================================

The preferred first reconciliation unit is:

STOP EVENT

rather than assuming complete journey equality.

Example:

MDD:

Line 18
Köln Neumarkt
scheduled 10:15
direction X
arrival

GTFS.de / GTFS-RT:

same canonical line
same canonical stop
same service date
same scheduled time
same direction
same event context

This can produce a high-confidence stop-event match.

If multiple consecutive stops also match:

Stop A
Stop B
Stop C
Stop D

with corresponding timetable sequence evidence, then confidence in
journey-level equivalence becomes much stronger.

Document:

multiple consistent stop-event matches
>
single stop-event match
>
route/time proximity only

==================================================
12. RECONCILIATION CONFIDENCE
==================================================

Define conceptual match levels:

HIGH

MEDIUM

LOW / UNMATCHED

HIGH:

Strong identity agreement across sufficient dimensions such as:

- service date;
- canonical stop;
- canonical line;
- scheduled time;
- direction where available;
- event type;
- stop sequence or multi-stop consistency where available.

A HIGH match may be used for trip/service-level cross-source attribution.

MEDIUM:

Useful evidence exists but one or more important identity dimensions are
missing or ambiguous.

MEDIUM matches may be used for contextual analysis.

They must NOT be used to make strong trip-specific cause claims.

LOW / UNMATCHED:

Only weak overlap exists, for example:

- same route;
- same station;
- same broad time window;
- same operator.

Do NOT attribute GTFS-RT alert/cause to an MDD trip.

15. TRIP-SCOPED ALERT
==================================================

If a GTFS-RT ServiceAlert explicitly references:

trip_id

and that trip has a HIGH-confidence reconciliation to an MDD/canonical service
event:

then the project may associate the alert with the matched service.

Permitted language:

"GTFS-RT reported this alert for the matched service."

If the Alert contains cause/effect semantics, permitted fields may conceptually
include:

ReportedCause
ReportedEffect
AlertSource = GTFS_RT
AssociationLevel = TRIP
MatchConfidence = HIGH

Do NOT call it proven root cause.

==================================================
16. ROUTE-SCOPED ALERT
==================================================

If an Alert references only:

route_id

then it must NOT automatically become the cause of every delayed journey on
that route.

Permitted interpretation:

"A route-level alert was active for the service context."

AssociationLevel:

ROUTE

Even if the MDD journey belongs to that route, do not turn the route Alert into
a trip-specific causal assertion unless stronger source linkage exists.

==================================================
17. STOP-SCOPED ALERT
==================================================

If an Alert references a stop:

"A stop-level alert was active at this in-scope stop."

"This alert caused the delay of this trip."

AssociationLevel:

27. GTFS-RT COLOGNE FILTERING
==================================================

The future GTFS-RT collector/design should eventually keep only relevant
Cologne evidence.

An entity may be considered potentially relevant when:

A. its stop maps to an in-scope Cologne canonical stop;

OR

B. its trip can be reconciled to an in-scope Cologne service event;

OR

C. its Alert explicitly references an in-scope Cologne stop;

OR

D. its Alert references a trip that has in-scope Cologne service events;

OR

E. its route-level Alert affects a route with an active in-scope Cologne
service context.

Do not yet define the final persistence algorithm.

28. ALERT RELEVANCE FILTERING
==================================================

Do not persist every Germany-wide ServiceAlert into the analytical layer.

A ServiceAlert should enter the Cologne analytical context only when it has a

- an in-scope Cologne stop;
- an in-scope Cologne service/trip;
- an in-scope Cologne route context;
- or another explicitly approved Cologne operational entity.

Agency-wide alerts require special handling because they may be too broad.

They should not automatically enter trip-level KPI calculations.
