## Analyze timing evidence

Measure from actual SQL data:

- Scheduled/timetabled arrival availability
- Estimated arrival availability
- Estimate revision frequency
- First/latest observed estimate
- Last non-NULL observed estimate
- Source-provided `RecordedAtTime` occurrence counts
- `LastObservedRecordedAtTime` availability
- Ambiguous source-event identities
- Missing timing and parser-gap classifications
- Arrival versus departure context
- `THIS` versus `PREVIOUS` versus `ONWARD` call context

Preserve all timing semantics.

`RecordedAtTime` must not be inferred from a prediction or capture timestamp.

A last-known non-NULL RecordedAtTime must remain available for reporting without replacing later source-NULL observations.

Estimated delay must never be labeled actual physical delay.

## Investigate delay hotspots

Determine whether the current evidence can support:

- Delay distributions by monitored station
- Delay distributions by line/service
- Time-of-day patterns
- Repeated high-delay locations
- Estimated-delay increases between consecutive stops
- Dwell-related hypotheses where source coverage permits

Use appropriate unique-event grains.

Never rank stations based only on raw observation counts.

Report denominators, temporal coverage, sampling era, matching quality, and missing data.

Legacy7 must remain explicitly labeled as a limited monitoring panel.

Köln Neumarkt is not a Legacy7 production target. Do not present it as an observed production hotspot without qualifying the evidence source.

## Investigate downstream propagation feasibility

Check whether the available records support defensible association of consecutive stop calls to the same vehicle journey and service date.

Evaluate:

- Source journey identity stability
- Stop sequence availability
- Stop identity resolution
- Direction and line consistency
- Scheduled stop order
- Repeated observations
- Previous/This/Onward context
- Temporal consistency
- Ambiguous journey matches

Separate:

1. Observed estimated-delay change
2. Candidate downstream delay propagation
3. Provider-reported disruption association
4. Proven causal attribution

Do not upgrade one evidence level into another.

If reliable journey continuity cannot be established, report `INSUFFICIENT_EVIDENCE` and identify exactly what is missing.

## Analyze provider-reported causes

Inspect persisted Situation and Attribute evidence.

Measure:

- Number of records with source Situation evidence
- Explicit disruption or cause codes where available
- Situation identity and version continuity
- Source-reported affected lines and journeys
- Linked versus unlinked situations
- Missing or ambiguous cause classifications
- Historical changes in provider-reported descriptions

Keep source-reported cause information separate from analytically inferred propagation.

Do not infer cause from free text alone.

A Situation association must not be reported as proof that the situation caused a specific delay.

If the current source lacks sufficient cause coverage, quantify that limitation.
