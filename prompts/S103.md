## Make dedicated-login provisioning recovery-safe

The current provisioning sequence commits the generated SQL login/password before the final Keychain write.

A Keychain failure after SQL commit can leave a login whose generated password is no longer durably available to the runtime.

Harden this flow.

The password must never be printed or written to Git/runtime JSON/plist/logs.

Use a secure two-phase or equivalent recovery-safe design.

An acceptable pattern is:

- generate the candidate password in memory;
- preserve it temporarily in a dedicated pending macOS Keychain item;
- create/rotate the SQL login using that exact candidate;
- validate positive and negative permission boundaries;
- write/promote the final approved Keychain item;
- update owner-only non-secret runtime config;
- remove the pending Keychain item only after final success.

If finalization fails after SQL password change:

- retain a recoverable pending Keychain credential;
- report a sanitized `CREDENTIAL_FINALIZATION_RECOVERY_REQUIRED` state;
- keep LaunchAgent disabled;
- support a deterministic resume/finalize path without generating another unknown password.

Do not expose the secret in the recovery report.

For an existing runtime login, do not rotate its password unless explicitly requested or recovery requires it.

Add tests for:

- successful first provisioning;
- Keychain-finalization failure;
- safe resume;
- existing-login no-rotation refusal;
- explicit rotation;
- no secret leakage.
