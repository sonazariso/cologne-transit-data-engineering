## Stage 9 Scope

Complete **Stage 9 — Matching & Data Quality** end-to-end.

The project is being rebuilt toward the final architecture, including the future **Tiered50 collector, operational analytical layer, and Power BI reporting**.

Therefore, Stage 9 must not be implemented as an isolated temporary solution.

You MAY modify existing shared implementation when the modification is necessary to make Stage 9 correct and future-compatible, including:

- MDD/TRIAS parser logic;
- collector data contracts;
- persistence models;
- SQL staging structures;
- working-layer views;
- matching-related indexes;
- shared helper functions;
- source identity fields;
- data-quality classifications;
- documentation and contracts.

If Stage 9 evidence shows that an earlier Stage 0–8 assumption or implementation is wrong, incomplete, or insufficient, **fix it now rather than preserving it artificially**.

Any such change must:

1. be justified by evidence;
2. preserve existing historical data where applicable;
3. preserve source-faithful semantics;
4. avoid fabricating missing information;
5. remain compatible with the planned Tiered50 architecture.

### Future architecture awareness

Stage 9 matching must be designed so that it can later operate correctly when the collector expands from the current small pilot to **Tiered50**.

Consider scalability and deterministic behavior for:

- 50 monitored stations;
- higher realtime observation volume;
- repeated observations of the same scheduled event;
- different sampling cadences;
- richer source identity fields;
- historical continuity between sampling eras.

Do not hardcode assumptions that only work for the current small Stage 8 pilot.

### What not to complete yet

The focus of this branch remains Stage 9.

Do not independently declare the following later stages complete:

- Stage 10 — Operational Fact
- Stage 11 — Power BI Model
- Stage 12 — 50-Station Selection
- Stage 13 — Tiered Collector Readiness
- Stage 14 — Controlled Tiered50 Cutover
- later stages

However, **do not avoid necessary Stage 9 changes merely because the affected code or schema will also be used by those future stages**.

For example:

- if the collector must persist an additional identity field required for reliable matching, add it;
- if staging must expose richer matching evidence, change it;
- if an index is required for deterministic/scalable Stage 9 matching, add it;
- if a current parser assumption prevents correct matching, fix it;
- if a shared contract must change so Tiered50 can later use the validated matching logic, update it.

The distinction is:

> **Make every change required to correctly complete Stage 9 and prepare a sound foundation for the final architecture, but do not execute or mark later stages complete.**

At the end, Stage 9 should be a production-quality matching/data-quality foundation that Stage 10 and Tiered50 can build on directly, not a throwaway pilot implementation.
