## 1. Add safe API-key format preflight

During the real Stage 8 troubleshooting, an `MDD_API_KEY` value containing a hidden Unicode U+2028 character caused Python's HTTP header encoding to fail before any request reached MDD.

That failure was reported through the transport boundary as `NETWORK_OR_DNS_FAILURE`, which was misleading because no DNS/network operation was the real cause.

Fix this at preflight.

Before:
- creating a temporary evidence directory;
- building/sending an HTTP request;
- or entering the network transport path;

validate only that the credential is structurally safe for the HTTP header used by this project.

Requirements:

- Never print the API-key value.
- Never hash, fingerprint, persist, or log the API-key value.
- Do not normalize or silently modify the credential.
- Do not automatically strip Unicode or whitespace and then use the modified value.
- If the value is empty, preserve the existing `MDD_API_KEY: MISSING` behavior.
- If the value contains characters that cannot safely be used in the HTTP header, stop locally before HTTP and classify the condition explicitly as:

  `CREDENTIAL_FORMAT_INVALID`

- The user-visible preflight output may state only a safe status such as:
  `MDD_API_KEY: INVALID_FORMAT`
  without exposing the offending character, position, credential length, hash, or any derived secret information.

For this invalid-format path:
- HTTP attempts must be zero;
- no MDD request may be issued;
- no temporary raw-response directory should be created merely for this preflight failure;
- do not classify it as NETWORK_OR_DNS_FAILURE;
- do not classify it as MDD authorization failure.

Apply the same safe preflight behavior to both:
- `stage_08_authorization_request_contract_diagnostic.py`
- the shared Stage 8 pilot entry path / shared credential boundary where appropriate,

without duplicating conflicting validation logic.

Offline validation must prove:
- missing key -> existing missing-key result;
- ordinary valid ASCII credential-shaped test value -> preflight accepted;
- test value containing U+2028 -> `CREDENTIAL_FORMAT_INVALID`, zero HTTP attempts;
- newline/carriage-return contamination -> invalid format, zero HTTP attempts;
- no credential content appears in output or artifacts.

Do not use a real API key for the offline tests.

## 2. Preserve bounded raw evidence when RecordedAtTime is actually observed

The future observation contract already correctly requires durable parsed preservation of:

- exact source `RecordedAtTime`;

- first-seen `RecordedAtTimeObservedAt`;
- append-only later observations;
- no erasure by later NULL/disappearance.

The remaining gap is raw forensic evidence.

The completed Stage 8 pilot cleaned all successful raw payloads immediately after successful reconciliation. That was correct under the original Stage 8 contract, but the project now has an explicit requirement that if a rare source-provided `RecordedAtTime` appears during future collection/validation, its temporary raw evidence must not disappear before it can be reviewed.

Implement a narrowly bounded evidence-retention mechanism for future executions.

- persist the parsed source-faithful RecordedAtTime evidence exactly as already required;
- mark that response as `RECORDED_AT_TIME_RAW_EVIDENCE`;
- retain the corresponding raw response in the protected temporary evidence area instead of deleting it immediately during normal successful cleanup;
- keep normal directory/file permission rules (`700` directory / `600` files);
- verify again that no API-key value or authorization material is stored;
- never commit, publish, or move the raw response into Git;
- never make raw payloads the authoritative warehouse source.

Do not retain every successful response merely because this feature exists.

### Bounded retention

Do not introduce permanent raw storage.

For now, keep this special raw evidence within the already approved maximum temporary boundary of 24 hours.

Do not invent a 7-day, 14-day, or permanent retention policy in this task.

A longer production retention period, if wanted later, requires a separate explicit user decision based on storage, privacy/provider terms, and operational cost.

The summary/cleanup result must make the distinction explicit:

- ordinary successful response artifacts may be cleaned normally;
- successful run with retained positive RecordedAtTime raw evidence must report that bounded evidence is intentionally retained and give its maximum deletion deadline;
- failed/blocked diagnostic evidence continues to use the existing bounded failure retention behavior.

Do not call intentional RecordedAtTime evidence retention a cleanup failure.

Use a clear non-error status such as:

`RECORDED_AT_TIME_EVIDENCE_RETAINED_MAX_24_HOURS`

or an equivalent explicit value.

### Sanitized durable evidence

The full raw response remains temporary, but the small source-faithful Parsed RecordedAtTime record and its lineage must remain the durable evidence.

Do not require the full raw payload to survive permanently in order to use the parsed field later.
