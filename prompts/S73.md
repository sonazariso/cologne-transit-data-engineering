## 1. Fix duplicate dispatcher invocation and flaky concurrency

The current concurrent duplicate test is nondeterministic.

Repeated full-suite executions have produced failures where the expected 19 simulated transport calls became values such as 2, 4, or 7.

Root issue:

- two concurrent `run_once()` calls can create separate ThreadPoolExecutors;
- both use the same collector active-worker counter;
- aggregate active workers can exceed the approved cap;
- `_enter_worker()` raises instead of coordinating execution;
- target futures then fail nondeterministically.

More importantly, the approved Stage 13 contract says a duplicate dispatcher invocation for the same logical bucket must issue zero HTTP requests.

Implement an atomic dispatcher/heartbeat claim before per-target execution.

Development identity:

`(panel_version, logical_due_bucket)`

Future production adapter must provide an equivalent durable dispatcher-bucket claim.

Requirements:

- first dispatcher claimant wins;
- duplicate invocation for the same panel/bucket performs zero target transport calls;
- duplicate dispatcher outcome is auditable;
- no second ThreadPoolExecutor performs work for the same bucket;
- behavior must work across separate persistence connections/process-equivalent collector instances, not only two threads sharing one Python object.

Do not rely only on an in-memory mutex.

SQLite must enforce the development dispatcher claim transactionally.

Add a dedicated durable dispatcher/bucket claim table or equivalent unique transactional mechanism.

## 6. Make quota attempt authorization atomic

The current quota guard performs:

read usage → decide → later record attempt.

With concurrency 2, two workers may both observe the same remaining headroom and both proceed.

Introduce an atomic quota-attempt authorization/reservation contract.

At minimum distinguish:

- scheduled initial-attempt permit;
- automatic-retry permit.

For SQLite development behavior, the permit/reservation must be durable and transactional.

Two concurrent retry decisions at the boundary must not both consume the same final unit of retry headroom.

Example regression:

- projected shared-credential total = 207,499;
- two retries race;
- at most one retry permit may be granted;
- projected permitted consumption must never exceed 207,500.

Likewise protect the 210,000 normal initial-request maximum.

Design the persistence/usage port so the future PostgreSQL adapter can implement the same atomic contract.

Do not solve this only with an in-memory Python lock.
