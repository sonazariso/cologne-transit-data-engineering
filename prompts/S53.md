# 4. First/latest timing semantics and NULL handling

This is critical.

`LatestObservedEstimatedArrivalUtc` must mean:

> the estimated arrival value contained in the chronologically latest observation.

It must **not** silently mean:

> latest non-NULL estimate seen historically.

Therefore, if an earlier observation contains an estimate but the latest observation contains NULL:

```text
LatestObservedEstimatedArrivalUtc = NULL
FinalObservedEstimatedDelayMinutes = NULL
```

Do not carry an older estimate forward.

Do not:

- replace NULL with timetable values;
- infer On Time from NULL;
- use `COALESCE` to hide unavailable timing;
- invent an actual arrival;
- substitute departure evidence for arrival timing.

Likewise, verify that first-observation timing fields come from the actual first observation row and not from `MIN`, `MAX`, or first-non-NULL logic.

Use NULL-safe validation.

If existing column names are slightly imperfect but their established meaning is clear, prefer documenting and validating the semantics rather than introducing unnecessary breaking schema renames.

# 6. Platform evidence semantics

Preserve conservative evidence semantics.

`PlatformChangeEvidence` must have only:

```text
Changed
Unchanged
Unknown
```

Interpretation:

### Changed

At least one observation has both a usable planned bay/platform and estimated bay/platform and they differ.

### Unchanged

There is comparable planned/estimated platform evidence and all comparable evidence supports equality, with no changed evidence.

### Unknown

There is no comparable planned/estimated platform evidence.

Treat NULL, empty and whitespace-only platform values as unavailable evidence.

Important:

```text
Unknown != Unchanged
```

Do not infer platform stability from missing data.

Validate the stored classification against all observations belonging to the fact grain.
