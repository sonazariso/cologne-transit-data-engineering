## Close the concurrent-resume race

The resume implementation uses SQL row locks during validation but commits the transaction before enabling the LaunchAgent and recording the resume event.

Two resume invocations with different keys can therefore pass the initial checks concurrently.

Implement durable or properly scoped exclusive resume-operation coordination.

Requirements:

- Only one resume transition may operate at a time.
- Include validation, LaunchAgent state transition, and completion recording in the protected lifecycle.
- Use a correctly scoped SQL application lock or equally reliable exclusive transition mechanism.
- Do not rely solely on checking RUNNING collector rows.
- Ensure cleanup on exceptions and process termination.
- Avoid holding ordinary row locks unnecessarily across slow external OS operations if a dedicated application-level coordination mechanism can be used.
- Preserve idempotency for repeated use of the same resume key.
- A concurrent second resume must not disable a successfully activated first resume.
- Preserve immutable SamplingEra, targets, and cutover history.
- Report aborted, incomplete, active and stopped transitions accurately.

Test simultaneous invocations with the same and different resume keys, including crash and retry scenarios.
