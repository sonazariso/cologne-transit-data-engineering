# 3. Business purpose of the model

The model serves a **non-technical operational/management audience**.

The primary management question remains:

> Is public transport within Cologne operating well during the selected period, based only on evidence the current data actually supports?

The semantic model must help answer:

- what network/schedule scope is represented;
- what operational evidence has been observed;
- where estimated timing problems appear;
- which lines/stops/modes are affected;
- where platform/bay changes are evidenced;
- where Situation evidence is associated;
- what proportion of evidence is unavailable;
- what Data Quality/matching limitations affect interpretation.

Technical details must remain available for drill-down but must not dominate the executive layer.

# 10. Threshold policy

Do NOT invent an official punctuality threshold.

Define a disconnected analytical parameter:

`Estimated Delay Threshold (Minutes)`

Recommended design range:

`0..15`

integer minutes.

Default:

`0`

The default represents no added tolerance assumption; it is NOT an official Cologne punctuality policy.

The resulting classifications must be named around **estimated delay**, for example:

- `Within Selected Estimate Threshold`
- `Estimated Delayed`
- `Estimated Early`
- `Timing Unavailable`

Do NOT call these categories official:

- On Time
- Punctual
- Late according to operator standard

unless a later approved business rule establishes that meaning.

NULL estimated delay must remain:

`Timing Unavailable`

and must never become Within Threshold.

Document clearly:

> The threshold is a user-selected analytical parameter, not source truth, provider policy, or actual physical punctuality.
